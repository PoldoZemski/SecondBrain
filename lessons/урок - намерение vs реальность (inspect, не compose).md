# Урок: намерение vs реальность (inspect, не compose)

## Случай
compose.yml содержал все нужные правки (токен через переменную, убранный user: root) и был датирован вечером дня работ. Контейнер при этом неделю жил СТАРОЙ конфигурацией: пересоздание после правок выполнено не было. Расследование строилось на чтении файла и неделю шло по ложному следу.

## Суть
- compose.yml - это НАМЕРЕНИЕ: что будет применено при следующем up
- docker inspect - это РЕАЛЬНОСТЬ: с чем контейнер запущен фактически
- Между ними - невыполненный (или выполненный до правок) up; дата файла ничего не говорит о дате применения

## Инструментарий проверки реальности
| Вопрос | Команда |
|---|---|
| Что смонтировано | docker inspect X --format '{{json .Mounts}}' |
| Какая команда/токены | docker inspect X --format '{{json .Config.Cmd}}' |
| От кого работает | docker inspect X --format '{{.Config.User}}' |
| Когда создан | docker inspect X --format '{{.Created}}' |
| Что БУДЕТ применено | docker compose config (с подстановками!) |

## Правила
1. Отладка расхождений начинается с inspect работающего контейнера, а не с чтения compose.yml.
2. Каждая правка compose завершается парой: up -d --force-recreate + inspect-проверка измененного поля. Правка без применения - мина замедленного действия (см. [урок - данные в контейнере без volume](%D1%83%D1%80%D0%BE%D0%BA%20-%20%D0%B4%D0%B0%D0%BD%D0%BD%D1%8B%D0%B5%20%D0%B2%20%D0%BA%D0%BE%D0%BD%D1%82%D0%B5%D0%B9%D0%BD%D0%B5%D1%80%D0%B5%20%D0%B1%D0%B5%D0%B7%20volume.md): между двумя потерями данных лежал именно неприменный фикс).
3. docker compose config показывает файл С подставленными переменными - быстрый способ увидеть будущую реальность до запуска.

## Интерфейс показывает не то, что лежит на диске
Тот же класс: «не вижу в интерфейсе» не равно «нет на диске», как «поправил compose» не равно «контейнер пересоздан». Проверять надо тем слоем, где объект реально живет: `ls` на сервере, а не проводник приложения. Подробности про Obsidian: [урок - obsidian это редактор markdown а не файловый менеджер](%D1%83%D1%80%D0%BE%D0%BA%20-%20obsidian%20%D1%8D%D1%82%D0%BE%20%D1%80%D0%B5%D0%B4%D0%B0%D0%BA%D1%82%D0%BE%D1%80%20markdown%20%D0%B0%20%D0%BD%D0%B5%20%D1%84%D0%B0%D0%B9%D0%BB%D0%BE%D0%B2%D1%8B%D0%B9%20%D0%BC%D0%B5%D0%BD%D0%B5%D0%B4%D0%B6%D0%B5%D1%80.md).

## Правишь один файл, работает другой

Правка конфига Xray не применилась: после restart порт остался на прежнем интерфейсе, хотя файл был отредактирован.

Причина - редактировался не тот файл. Проверяется командой:

```bash
systemctl cat <сервис> | grep ExecStart
```

Путь после -config и есть тот файл, который читает сервис.

Тот же класс: docker compose up -d без --force-recreate может не применить изменение лимитов и переменных. Правило прежнее - проверять живое состояние, а не содержимое конфига.
