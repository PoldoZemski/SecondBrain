# Урок: сеть между хостом и контейнерами

Опыт подключения n8n к Whisper и к Telegram через Xray.

## Ловушка первая: localhost внутри контейнера - это сам контейнер

Xray слушал на 127.0.0.1:10809. С хоста прокси работал (Claude Code ходил через него в API). Из контейнера n8n - ECONNREFUSED.

Причина: для процесса внутри контейнера 127.0.0.1 указывает на этот же контейнер, а не на хост. Сервис, слушающий localhost хоста, для контейнеров недоступен в принципе.

Решение: у нужного inbound listen меняется на 0.0.0.0, а контейнер обращается по адресу шлюза docker-сети (узнается командой `docker network inspect <сеть> --format '{{range .IPAM.Config}}{{.Gateway}}{{end}}'`).

Обязательное условие: порт закрывается файрволом от внешнего мира. При политике UFW deny (incoming) достаточно разрешить подсеть:

```bash
sudo ufw allow from 172.19.0.0/16 to any port 10809 proto tcp
```

Адреса 172.x приватные, из интернета такие пакеты не приходят. Подсеть у вас может быть другой: смотрите вывод docker network inspect.

Итоговое состояние (по `ss -tlnp`): 10808 слушает 127.0.0.1 (SOCKS), 10809 слушает все интерфейсы (HTTP). Claude Code использует 10809 через 127.0.0.1, контейнеры 10809 через шлюз. Вход 10808 остается локальным: открывать наружу нужно только то, что действительно нужно.

## Ловушка вторая: NO_PROXY для внутренних адресов

В контейнере n8n заданы HTTP_PROXY и HTTPS_PROXY. HTTP-нода работает на Node.js и эти переменные уважает: значит запрос к соседнему контейнеру (http://whisper:9000) тоже уйдет в прокси, где такого хоста нет.

Решение: перечислить внутренние имена в NO_PROXY:

```
NO_PROXY=whisper,localhost,127.0.0.1,second-brain-couchdb
```

## Ловушка третья: wget из BusyBox проверяет не то

Контейнеры на alpine содержат BusyBox-версию wget, которая читает переменные в НИЖНЕМ регистре (http_proxy), а заданы обычно заглавные. Проверка проходит успешно, но она шла напрямую, минуя прокси, и ничего о прокси не сказала.

Правильная проверка - с явным указанием:

```bash
sudo docker exec <контейнер> sh -c 'http_proxy=http://<шлюз>:<порт> wget -qO- --timeout=15 <url>'
```

## Ловушка четвертая: проверка снаружи через собственный VPN

Test-NetConnection с ноутбука показал открытый порт при политике UFW deny. В выводе была строка InterfaceAlias: xray_tun - запрос ушел через собственный туннель, который ведет на этот же сервер, то есть пришел изнутри доверенной сети.

С отключенным туннелем тот же тест дал TcpTestSucceeded: False.

Правило: проверка внешней доступности выполняется с машины, НЕ подключенной к инфраструктуре проверяемого сервера. В выводе смотреть InterfaceAlias и SourceAddress: они показывают, каким путем реально пошел запрос.

## Диагностика по шагам
1. Что слушает и на каком интерфейсе: `ss -tlnp | grep <порт>`. Различать 127.0.0.1:порт (только хост) и 0.0.0.0:порт (все).
2. Какой конфиг читает сервис: `systemctl cat <сервис> | grep ExecStart`. Путь в ExecStart может отличаться от того, который правишь.
3. Шлюз docker-сети: `docker network inspect <сеть> --format ...Gateway`
4. Правила файрвола: `ufw status numbered`
5. Внешняя доступность: только с посторонней машины.

## Признаки, что урок не усвоен
* Прокси или сервис для контейнеров настроен на 127.0.0.1.
* Порт открыт на 0.0.0.0 без правила файрвола.
* Внешняя доступность проверена с машины под VPN.
* Проверка прокси через wget без явных переменных в нижнем регистре.
