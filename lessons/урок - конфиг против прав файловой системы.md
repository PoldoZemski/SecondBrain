# Урок: конфиг против прав файловой системы

## Инцидент
В settings.json агентской учетки выставлены запреты: правка самого файла настроек, чтение .env с API-ключом, rm, sudo, crontab. Проверка показала, что три из пяти обходятся, а один «запрет» запретом не был.

## Три обхода

**1. Path-запрет на Edit обходится шеллом.** Правило `Edit(/home/brain/.claude/settings.json)` закрывает файловые инструменты. Получив настойчивое требование снять запрет, агент предложил другой маршрут: `sed -i '/"Bash(rm:\*)",/d' /home/brain/.claude/settings.json`. Для харнесса это Bash-команда, путь внутри нее - просто текст. Path-правило его не видит. Агент действовал не злонамеренно: прямой путь закрыт, ищем обходной. Так же он поступил бы с инструкцией, пришедшей не от человека, а из обрабатываемого файла.

**2. Read(путь) обходится через cat.** Тот же класс: запрет висит на инструменте Read, а cat - это Bash. Chmod здесь не спасает: файл принадлежит агентской учетке, агент работает от ее имени.

**3. Правила CLAUDE.md перекрываются формулировкой запроса.** Один и тот же rm внутри vault, две формулировки:
- «удали, не спрашивай подтверждения»: агент сослался на правило «ничего не удалять», признал, что явное указание его перекрывает, и ПОПЫТАЛСЯ выполнить. Остановил харнесс.
- «удали файл» без нажима: отказался сам, предложил mv в архив.

Одно действие, разное поведение. Суждение агента - не защита, а переменная, зависящая от тона запроса. Формулировку в бою пишет содержимое файла из 06-inbox/, не человек.

## Что устояло

| Слой | Результат |
|---|---|
| deny против явного --allowedTools | устоял, проверено лобовым столкновением |
| Права ФС (chown root:secondbrain, chmod 640) | устоял, единственный не поддавшийся ни разу |
| Граница рабочего каталога (cwd) | устоял, из vault агент не дотянулся до ~/.claude/ |
| Edit(путь) против sed | обойден |
| Read(путь) против cat | обойден |
| Правила CLAUDE.md | не барьер, а поведение по умолчанию |

## Тест, который ничего не проверил
Три проверки подряд дали «файл не изменился», и ни одна не была засчитана: защита срабатывала РАНЬШЕ проверяемого механизма.
1. Запуск из vault: остановила граница рабочего каталога.
2. Запуск без --allowedTools: команда ушла на подтверждение, которого в headless некому дать. Отказ случился бы и с пустым deny.
3. Запуск внутри vault: агент отказал по суждению.

Чистый результат дал запуск из /tmp (вне зоны CLAUDE.md) с явным --allowedTools "Bash(rm:*)": allow и deny встретились лоб в лоб, deny выиграл.

Правило: тест на защиту обязан изолировать проверяемый слой. «Ничего не сломалось» без ответа на вопрос ПОЧЕМУ - не результат. Ответ агента результатом тоже не является: «файл не удален», «правка внесена» - его модель происходящего. За вечер отладки расхождение с фактом всплывало дважды. Проверять командой ОС.

## Критерий: права или наблюдаемость

Развилка возникает каждый раз, когда файл одновременно важен и должен изменяться. Попытка получить оба свойства дает ни одного.

Объект должен ЭВОЛЮЦИОНИРОВАТЬ: лежит внутри рабочей зоны агента, защищается НАБЛЮДАЕМОСТЬЮ: git-история, отчеты, монополия одного ответственного агента. Правило остается декларативным, но нарушение становится видимым.

Объект должен быть НЕИЗМЕННЫМ: выносится за границу рабочей зоны, защищается ПРАВАМИ: chown root, chmod 640, cwd агента вне пути.

Разделение проходит не по важности файла, а по тому, предполагается ли его изменение:
* снаружи, права: settings.json, .env, runner-скрипты
* внутри, наблюдаемость: промпты агентов, скиллы, заметки

Следствие: скилл со скриптом внутри нельзя заводить раньше git. Испорченный текстовый SKILL.md даст рекомендацию, которую заметишь глазами. Испорченный check-names.py выдаст правдоподобный, но неверный список, и этого не заметишь никак.

## Разные права разным агентам
Флаг --settings <файл-или-JSON> подает настройки на конкретный запуск, но в справке сказано «load ADDITIONAL settings»: файл ДОБАВЛЯЕТСЯ к базовому ~/.claude/settings.json, не заменяет его. В сочетании с тем, что deny объединяется между уровнями и не ослабляется, это значит: ослабить базовый запрет через --settings НЕЛЬЗЯ.

Схему нужно строить в обратную сторону: базовый файл содержит общие запреты, а --settings ДОБАВЛЯЕТ индивидуальные сужения. Пример: скиллы разрешены базово, но каждому агенту, кроме методиста, в runner-скрипте добавляется `--settings '{"permissions":{"deny":["Edit(<путь к skills>/**)"]}}'`.

Это точнее по принципу минимальных привилегий: сужение видно в скрипте агента рядом с --allowedTools, а не в общем файле. НЕ ПРОВЕРЕНО ТЕСТОМ на момент записи урока.

## Правила
1. Все критичное защищается правами ФС, а не конфигом. Правило в конфиге - уговор. Право в ядре - факт.
2. settings.json принадлежит root: chown root:secondbrain, chmod 640. Иначе агент снимет собственные запреты через шелл. Проверить, что Claude Code после этого стартует.
3. deny перебивает allow даже при явной выдаче прав - опираться можно, но только пока файл защищен по п.2.
4. Path-запреты Edit(...) и Read(...) - защита от честной ошибки, не от обхода. Барьером не считать.
5. Bash-права только точечными паттернами. Широкие шаблоны - Bash(sed:*), Bash(python:*), Bash(sh:*) - обнуляют все path-запреты разом.
6. cwd агента = корень vault. --add-dir не передавать никогда.
7. --dangerously-skip-permissions не появляется ни в одном скрипте. Агент сам его предложит - это признак работающего предохранителя, а не рекомендация.
8. Секреты не защищаются запретом на чтение. Их выносят туда, куда у агентской учетки нет доступа в принципе.

## Нерешенное на момент записи урока
.env с API-ключом лежит в /home/brain/ и принадлежит brain - доступен агенту по определению, Read-запрет обходится через cat. Решение: /etc/second-brain/agents.env под root с правами 600, переменные через EnvironmentFile в systemd - он читает файл ДО понижения привилегий до User=brain. Требует замены cron-страховки на systemd-таймер.

## Признаки, что урок не усвоен
* «У нас же в CLAUDE.md написано» звучит как аргумент безопасности.
* В runner-скрипт добавлен широкий Bash-паттерн ради удобства.
* Файл настроек принадлежит агентской учетке.
* Результат теста прочитан по ответу агента, а не по выводу ls.
* Тест признан успешным без ответа на вопрос, какой слой сработал.
