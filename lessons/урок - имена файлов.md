# Урок: имена файлов в кросс-платформенном хранилище

## Ловушка
Один и тот же vault живет одновременно на трех файловых системах с разными правилами: ext4 на сервере, NTFS на ноутбуке, APFS на iPhone. Плюс промежуточное звено, CouchDB, где имя файла становится идентификатором документа. Имя, законное в одном звене, в другом может быть недопустимым, схлопнуться с соседним или разойтись в байтах при внешне одинаковом виде.

Проявляется это не ошибкой, а тишиной: ссылка `[[заметка]]` перестает открываться, файл не доезжает на телефон, два файла превращаются в один. Ни одно звено не сообщает о проблеме.

## Что требуют файловые системы

| Звено | Регистр | Что еще запрещено |
|---|---|---|
| ext4 (сервер, Ubuntu) | значим: `Файл.md` и `файл.md` разные файлы | только `/` и нулевой байт |
| NTFS (Windows) | не значим, но сохраняется при записи | `\ / : * ? " < > \|`, точка и пробел в конце имени, зарезервированные имена: con, prn, aux, nul, com1-com9, lpt1-lpt9 |
| APFS (iOS/macOS) | по умолчанию не значим | `:` (историческое наследие) |
| CouchDB (LiveSync) | значим | имя документа не начинается с подчеркивания |

Практический вывод: работоспособный набор имен - это ПЕРЕСЕЧЕНИЕ всех ограничений, а не то, что разрешает самая мягкая система. Сервер разрешает почти все, поэтому проверять надо по Windows.

## Отдельные ловушки кириллицы

1. **Буква «е» и буква «е с двумя точками».** Визуально почти неразличимы, но это разные символы. Два файла, имена которых отличаются только этой буквой, - разные файлы, и ссылка на один не откроет другой. В промптах агентов эта пара расходится особенно легко: в тексте пишут букву с точками, в пути копируют обычную «е». Решение: буква «е с двумя точками» в именах не используется вовсе.

2. **Нормализация Unicode.** Символы с диакритикой (й, «е с двумя точками») могут храниться либо одним кодом (NFC), либо базовой буквой плюс знаком (NFD). Внешне имена идентичны, побайтово - нет. Системы Apple исторически тяготеют к NFD, Linux - к NFC. Это дает класс ошибок "файл есть, но не находится". Отказ от буквы с точками снимает большую часть риска; «й» остается, поэтому при необъяснимо битой ссылке проверяй байты: `ls | hexdump -C | grep <фрагмент>`.

3. **Кириллица и латиница.** Русская «с» и латинская «c» неразличимы на глаз. При копировании имени из смешанного текста легко получить гибрид, который не найдется ни по одному написанию. Случай из проекта: файл «урок - couchdb - это не файлы.md» был создан с кириллической «с» в слове couchdb. Обнаружен только при выводе find по всему vault, визуально имя выглядит корректным. Ссылка, набранная в латинице, цели не находит. Проверка: `ls | grep -P "\x{0441}"` (кириллическая «с»), или общий поиск смешения алфавитов внутри слова. Глазами этот класс ошибок не ловится, только кодом.

## Правило
* Нижний регистр, кириллица и латиница одинаково.
* Пробелы в именах допустимы.
* Буква «е с двумя точками» не используется.
* Никаких тире, типографских кавычек и символов из колонки NTFS.
* Проверка нового имени - по строке Windows, она самая строгая.
* Исключения: SKILL.md, CLAUDE.md и README.md - имена жестко заданы инструментами.

Скрипт проверки всего хранилища: [шаблон скилла naming-check](../starter/%D1%88%D0%B0%D0%B1%D0%BB%D0%BE%D0%BD%20%D1%81%D0%BA%D0%B8%D0%BB%D0%BB%D0%B0%20naming-check.md).

## Схема безопасного переименования
Переименование, отличающееся ТОЛЬКО регистром (`Заметка.md` в `заметка.md`), на Windows и iOS не является переименованием вовсе: для этих систем это одно и то же имя. Операция либо не применится, либо породит конфликт в CouchDB. Поэтому:

1. Переименовывай **в два шага, через промежуточное имя**: `Заметка.md`, затем `заметка-tmp.md`, затем `заметка.md`. Оба шага однозначны на любой файловой системе.
2. Делай это в Obsidian на десктопе, а не через `mv` на сервере: Obsidian сам обновит все ссылки на файл. Через `mv` ссылки останутся битыми, и чинить их придется отдельно.
3. Партиями по 10-20 файлов, с проверкой синхронизации на телефоне после каждой партии. Массовое переименование всего vault разом через LiveSync дает лавину конфликтов.
4. Перед партией - коммит в git (см. главу [15-резервные копии и обслуживание](../guide/15-%D1%80%D0%B5%D0%B7%D0%B5%D1%80%D0%B2%D0%BD%D1%8B%D0%B5%20%D0%BA%D0%BE%D0%BF%D0%B8%D0%B8%20%D0%B8%20%D0%BE%D0%B1%D1%81%D0%BB%D1%83%D0%B6%D0%B8%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5.md)). Это единственный способ откатить неудачное переименование.
5. После партии - прогон библиотекаря: он найдет ссылки, которые не обновились.

## Признаки, что урок не усвоен
* Ссылка не открывается, хотя файл видно в проводнике.
* Файл виден на ноутбуке, но не появляется на телефоне.
* Два файла с внешне одинаковым именем в списке на сервере.
* `grep` по имени не находит файл, который точно есть.
