# Урок: массовые изменения файлов только через сервер

Опыт загрузки зеркала внешнего справочного ресурса (248 файлов).

## Симптом

248 файлов узлов скопировали из архива прямо в папку хранилища на Windows с заменой. Через некоторое время:
- около 40 файлов снова содержали старую версию со ссылками на README.md;
- 25 новых файлов Obsidian не видел;
- у части файлов текст в начале менялся между проверками: их кто-то перезаписывал.

Содержимое на диске Windows и то, что показывал Obsidian, расходилось.

## Причина

По моему непроверенному мнению: копирование в обход Obsidian конфликтует с LiveSync. Obsidian и LiveSync не регистрируют часть внешних изменений. Для части файлов LiveSync вернул из CouchDB старые версии. Точный механизм не проверялся.

Проверенный факт: тот же набор файлов, записанный на сервере скриптом, дошел до Obsidian полностью и без конфликтов.

## Решение

Массовые изменения файлов в хранилище выполняются на сервере, тем же путем, что у агентов:

диск VPS, затем [04-мост в файлы (livesync-bridge)](../guide/04-%D0%BC%D0%BE%D1%81%D1%82%20%D0%B2%20%D1%84%D0%B0%D0%B9%D0%BB%D1%8B%20%28livesync-bridge%29.md), затем CouchDB ([03-синхронизация obsidian](../guide/03-%D1%81%D0%B8%D0%BD%D1%85%D1%80%D0%BE%D0%BD%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F%20obsidian.md)), затем Obsidian на устройствах.

Скрипт пишет файлы по одному, с паузой 0,5 секунды. Каждая запись дает одно событие inotify, и livesync-bridge успевает его обработать. Скрипт пишет только измененные файлы и ничего не удаляет.

## Чем не стоит пользоваться для массовых изменений

- Копирование файлов в папку хранилища на Windows с заменой: конфликт с LiveSync, описан выше.
- `mv` папки целиком, `rm *` по папке: одно событие inotify на всю папку, в CouchDB остаются «призраки». Это правило 8 в CLAUDE.md ([шаблон claude.md, часть 1](../starter/%D1%88%D0%B0%D0%B1%D0%BB%D0%BE%D0%BD%20claude.md%2C%20%D1%87%D0%B0%D1%81%D1%82%D1%8C%201.md)).
- Коннектор Obsidian из чата Claude Desktop. Он пишет один файл за вызов. Сотни вызовов подряд в одном чате ненадежны: вызов может зависнуть на 4 минуты, а в длинном разговоре инструменты коннектора перестают загружаться. Коннектор подходит для десятка карточек, а не для сотен.

## Внешнее зеркало: правка должна жить в генераторе

Ручная правка файлов зеркала пропадает при следующем обновлении. Пример: ссылки на несуществующий README.md заменили в файлах, но генератор снова создавал их со старой ссылкой. Правильное место для такой правки - сам скрипт обновления: замена ссылки встроена в генератор отдельным шагом и проверяется в конце каждого запуска.

По той же причине шапки YAML в файлах зеркала не приводятся к стандарту хранилища. Стандарт применяется к корневой карточке ресурса.

## Перемещение каталога на сервере

Случай: при разборе папки 49 карточек перенесли в архив на сервере вместе с каталогом. На диске файлы лежали на новом месте, а в CouchDB их не было, и в Obsidian папка осталась пустой. Причина: при перемещении каталога ядро выдает одно событие на сам каталог, событий на файлы внутри нет, и мост о них не узнает. Для таких случаев работает сторож синхронизации: [08-сторож синхронизации](../guide/08-%D1%81%D1%82%D0%BE%D1%80%D0%BE%D0%B6%20%D1%81%D0%B8%D0%BD%D1%85%D1%80%D0%BE%D0%BD%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D0%B8.md). Сторож не убирает старые документы из CouchDB: старую копию удаляют в Obsidian.

## Правило

1. Изменение затрагивает больше десятка файлов: скрипт на сервере, запись по одному файлу с паузой.
2. Перед рабочим прогоном - пробный прогон без записи (`--dry-run`).
3. После прогона - проверка в Obsidian: число файлов и отсутствие старых значений.
4. Правка зеркала внешнего ресурса - только в генераторе.

## Признаки, что урок не усвоен

- Файлы копируются в папку хранилища на Windows пачкой.
- После массовой правки в Obsidian видны старые версии части файлов.
- Ссылка или поле в файлах зеркала «чинятся» руками, а через месяц возвращаются.
